# Clinician-Only OSA Phenotyper Architecture

## Decision

The application is an internal clinical system. Only Capital ENT clinicians and authorized staff can authenticate. Patients never log in, and the AWS stack exposes no anonymous application or API route. Patient reports are generated by staff and transferred through the EHR or another approved workflow.

This reduces the most consequential failure mode: a reusable or guessable public link exposing PHI. It also removes the ability for one authenticated browser request to retrieve the practice's full patient roster.

## Request path

```text
Authorized workforce device
  -> CloudFront + WAF (TLS, rate limits, managed rules)
  -> Cognito (mandatory MFA, clinician/admin group)
  -> API Gateway JWT authorizer
  -> Lambda origin-secret verification + route authorization
  -> DynamoDB patient table (KMS, PITR)
```

The API Gateway default hostname remains technically addressable on the internet, but direct requests do not possess the header secret injected by CloudFront and receive `403`. A valid Cognito token and the proper Cognito group are still required after that check.

## Data-access constraints

- `GET /patients` does not exist.
- `GET /patients/search` supports exact DOB, exact MRN, exact full name, and beginning-of-name search.
- Every DynamoDB query has `Limit: 10`; there is no `Scan` permission in the Lambda role.
- Archived charts are visible only to admins and still require a specific search.
- `GET /patients/{id}` writes a `patient_record_viewed` audit event containing the chart ID and workforce identity, but no clinical content.
- Searches write a `patient_search` event containing search type and result count, but never the search text.
- Clinical writes use optimistic version checks, preserving protection against silent overwrites.

## Patient report workflow

1. A clinician reviews the inputs and recommendations.
2. The clinician generates the patient PDF and may save a frozen snapshot in the chart.
3. Staff upload the report to the EHR for portal delivery, or use an approved email process after patient approval and in accordance with Capital ENT policy.
4. The OSA app does not retain delivery addresses, send email, host patient pages, or create bearer links.

## Precision Sleep v1 longitudinal workflow

- The hub stores structured follow-up checkpoints, not narrative encounter notes.
- Each checkpoint records the treatment pathway, pathway status, patient response, adherence, next action, and optional weight/ESS/ISI/AHI.
- Values are server-validated against fixed choices and clinical ranges; arbitrary follow-up text is not accepted.
- The API adds the authenticated workforce identity and timestamp. The client cannot choose them.
- Each chart retains at most 20 checkpoints to bound item growth and limit unnecessary longitudinal PHI.
- The EHR remains the legal record for the full note, prescriptions, orders, patient communication, scheduling, and billing.

Ordinary unencrypted email should not be treated as the default. The EHR is the preferred distribution channel because it keeps identity verification and delivery auditability in the existing clinical system.

## Low-cost AWS posture

The design remains serverless and pay-per-use: private S3, CloudFront, HTTP API, Lambda, DynamoDB on-demand, Cognito, KMS, WAF, CloudTrail, and CloudWatch. No always-running EC2 instance, load balancer, RDS database, patient identity system, or separate portal is required.

The main security-related recurring costs are WAF, KMS, audit-log storage, and normal request/storage usage. These controls should not be removed merely to reach a literal zero-dollar security budget.

## Required production controls outside the code

Before real PHI is entered, Capital ENT should document and verify:

- AWS account and every service in scope are covered by the active BAA.
- A formal HIPAA security risk analysis identifies this system, its users, data flows, and residual risks.
- Production uses a dedicated stack/table and is not the existing staging deployment.
- Workforce accounts are individual (never shared), promptly disabled at separation, and reviewed at least quarterly.
- Admin membership is limited; clinicians cannot archive/restore charts or manage users.
- Managed Capital ENT devices use disk encryption, screen lock, current patches, endpoint protection, and remote-wipe capability.
- CloudWatch alarms cover authorization failures, Lambda errors, WAF blocks, and unexpected request volume.
- DynamoDB recovery and audit-log retrieval are tested, not merely enabled.
- Incident response, breach assessment, downtime, report-delivery, and patient-email-approval procedures are written and trained.
- A production penetration test and application security review are completed after the final domain/network configuration.

## Optional network restriction

An office/VPN IP allowlist can further reduce exposure, but it should be enabled only when Capital ENT has stable egress addresses and an approved remote-access path. MFA, group authorization, bounded search, origin verification, WAF, and auditing remain mandatory even with an allowlist.

## Risk statement

No internet-connected clinical system can honestly promise zero risk. This architecture is designed to make a single credential, URL, or API call insufficient for a large-scale disclosure and to make access attributable and detectable. HIPAA compliance remains a combination of the technical configuration and Capital ENT's administrative and physical safeguards.
